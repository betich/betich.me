Around the middle of last year, my team and I were building a design system to be built dynamically using design tokens at work — an extensive one, with components and tokens to be changed frequently. The UX/UI team handed us design tokens in the [DTCG](https://tr.designtokens.org/format/) format, Tailwind v4 had just come out, and we had to figure out how to get from one to the other. And along with that, we built a custom Shadcn registry builder to make it easy for other developers to use our design system too.

I've since rewritten the gist of that system as a public repo:

The whole thing is really two builders stacked on top of each other.

**The first one turns token JSON into CSS.** [Style Dictionary](https://styledictionary.com/) does most of the heavy lifting. Its build is a pipeline you can hook into at almost every stage — parsers, preprocessors, transforms, formats, actions:

_Diagram from the [Style Dictionary docs](https://styledictionary.com/info/architecture/)._

The red labels are the extension points, and we ended up writing something at most of them — because at the time, Style Dictionary had no idea what Tailwind v4 was. Tailwind v4 derives its utilities from the _namespace_ a custom property lives in — `--color-*` gives you `bg-*` and `text-*`, `--spacing-*` gives you `h-*` and `p-*`, and a property that isn't in a namespace gives you nothing at all. So a token named `component.button.primary.bg.default` is useless until something renames it:

```
component.button.primary.bg.default  →  --color-button-primary-bg-default
                                     →  bg-button-primary-bg-default
component.button.size.md.height      →  --spacing-button-size-md-height
                                     →  h-button-size-md-height
```

That renaming is a Style Dictionary transform, and writing it was the part I enjoyed most — you're handed one token at a time and you decide what it becomes. Border widths are an exception: Tailwind has no `--border-width-*` namespace, so those keep their plain names and get read directly. The whole transform is about thirty lines: [`.sd/transforms/tailwindVarReference.ts`](https://github.com/betich/design-tokens/blob/main/.sd/transforms/tailwindVarReference.ts).

There's a [Tailwind v4 transformer for Style Dictionary now](https://github.com/tokens-studio/sd-tailwindv4). But there wasn't one when we needed it, so we read the CSS and SCSS transformers and built ours on top of those.

**The second one turns components into a registry.** shadcn's CLI isn't really a component library — it's a very smart file copier that knows about your project's structure. You point it at a JSON file describing a component and it writes the files into the right places. The docs for that are [here](https://ui.shadcn.com/docs/registry).

Writing those JSON descriptions by hand was not suitable for a design system that changes weekly. So instead, every component gets a `Component.registry.ts` sitting next to it, and we created a builder that combines and automatically creates the single JSON file instead. That way, everything is dynamic and interchangable without there being a tedious manual task.

```ts
export default defineRegistryItem({
  name: 'button',
  type: 'registry:component',
  title: 'Button',
  description: 'A button with four variants and three sizes.',
  categories: ['atoms'],
  files: [...],
  dependencies: [...commonDependencies, '@radix-ui/react-slot'],
})
```

`defineRegistryItem` is a [zod](https://zod.dev/) parse plus a transformation — it validates the metadata against the registry schema, and rewrites the component's dependencies from bare names into absolute URLs so that pulling `card` also pulls _our_ `button` instead of upstream shadcn's. That's [`src/.registry/build.ts`](https://github.com/betich/design-tokens/blob/main/src/.registry/build.ts), with the schemas in [`types.ts`](https://github.com/betich/design-tokens/blob/main/src/.registry/types.ts).

Discovery being a glob rather than a list matters more than it sounds. Adding a component means adding one file next to it — there's no central manifest file to forget to update, and the build fails loudly if the metadata is wrong rather than silently publishing something broken.
